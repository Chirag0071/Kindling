# Deploying Kindling

Three pieces: Aiven (database), Render (backend API), Vercel (frontend).
Set them up in that order — each step needs values from the one before it.

## 1. Database — Aiven Postgres

1. Create a Postgres service on [aiven.io](https://aiven.io) (the free tier works for this).
2. Once it's running, copy the **Service URI** from the Aiven console. It looks like:
   ```
   postgres://avnadmin:PASSWORD@your-service.aivencloud.com:PORT/defaultdb?sslmode=require
   ```
3. Keep `sslmode=require` in the URL — Aiven rejects unencrypted connections, and this is already handled by psycopg2 with zero code changes needed on our end.
4. Save this full URL — it's your `DATABASE_URL` for the next step.

## 2. Backend — Render

1. Push the `backend/` folder to a GitHub repo (Render deploys from GitHub).
2. In Render, **New > Blueprint**, point it at your repo. It'll pick up `render.yaml` automatically.
3. Fill in the env vars Render flags as needed:
   - `DATABASE_URL` → the Aiven URI from step 1
   - `FRONTEND_ORIGIN` → leave as a placeholder for now (e.g. `http://localhost:3000`), you'll update it after deploying the frontend
   - `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `S3_BUCKET_NAME` → **required**, see the warning below
   - `SECRET_KEY` is auto-generated by Render, you don't need to touch it
4. Deploy. Once live, note your API URL (`https://kindling-api.onrender.com` or similar) and check `/health`.

Render runs `alembic upgrade head` automatically before starting the app (see `startCommand` in `render.yaml`), so your Aiven database gets its schema created on first deploy with no manual migration step needed.

**⚠️ About photo storage on Render:** Render's filesystem is ephemeral — anything written to local disk disappears on every redeploy or restart. Our storage abstraction defaults to local disk when AWS credentials aren't set (that's what let us build and test photo upload without needing AWS access), but **on Render you must set the S3 credentials**, or every uploaded photo will vanish the next time the service restarts. This isn't optional for a real deployment.

## 3. Frontend — Vercel

1. Push `frontend/` to GitHub (same repo or separate, your call).
2. In Vercel, **Add New > Project**, import the repo, set root directory to `frontend/` if it's a monorepo.
3. Before the first deploy, set the environment variable:
   - `NEXT_PUBLIC_API_URL` → your Render URL from step 2
   
   This matters because Next.js inlines `NEXT_PUBLIC_` variables into the JS bundle at **build time**, not runtime — setting it after deploying won't work, you'd need to redeploy.
4. Deploy. Note your Vercel URL (`https://kindling.vercel.app` or similar).

## 4. Connect them

Go back to Render, update `FRONTEND_ORIGIN` to your actual Vercel URL, and redeploy the backend. Without this, the browser will block API requests with a CORS error.

## Known limitations to know about before real users touch this

- **Schema changes**: now handled by Alembic (`alembic revision --autogenerate -m "..."` after changing models, then commit the generated file). Render runs `alembic upgrade head` automatically on deploy.
- **Rate limiting** is per-IP, in-memory — resets on every Render restart, and won't be consistent if you ever scale to multiple instances.
- **WebSocket connections** are also in-memory and single-process — same caveat, would need Redis pub/sub to scale horizontally.
- **Free-tier Render services spin down after inactivity** and take ~30-60s to wake up on the next request — the first request after idle time will be slow. Fine for a demo, worth upgrading before real usage.
